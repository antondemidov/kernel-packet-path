Again from the bottom. The card raised an interrupt; on the way out of it the kernel runs the network softirq, net_rx_action(), which calls the driver’s NAPI poll, e1000e_poll(). When the poll is done, GRO hands over its batch, and __netif_receive_skb_core() processes the frame on nic0. nic0 is a bridge port, so its rx_handler is br_handle_frame(). The frame is addressed to the bridge itself, so br_pass_frame_up() passes it up: netif_receive_skb() runs a second time, now on vmbr0, and from there it is the usual ip_rcv() → ip_local_deliver() → tcp_v4_rcv(). All of it in one softirq, with no process involved.Знову знизу. Карта підняла переривання; на виході з нього ядро запускає мережевий softirq, net_rx_action(), а той — NAPI-опитування драйвера, e1000e_poll(). Коли опитування закінчено, GRO віддає свою пачку, і __netif_receive_skb_core() обробляє кадр на nic0. nic0 — порт бриджа, тож його rx_handler — br_handle_frame(). Кадр адресовано самому бриджу, тому br_pass_frame_up() передає його вгору: netif_receive_skb() виконується вдруге, тепер на vmbr0, а далі звичний ip_rcv() → ip_local_deliver() → tcp_v4_rcv().        0     0  sock_rfree                         ← skb_release_head_state

The last line of the trace. When the socket is destroyed, sk_stream_kill_queues() empties its receive queue, and every skb still there is freed with the drop reason SKB_DROP_REASON_QUEUE_PURGE. This one carried no data (len 0). sock_rfree() is the destructor of received skbs: it returns the memory to the socket’s accounting. A drop reason in a trace is therefore not always a lost packet; here it is an ordinary close.Останній рядок трасування. Коли сокет знищується, sk_stream_kill_queues() спорожнює його чергу прийому, і кожен skb, що там лишився, звільняється з причиною SKB_DROP_REASON_QUEUE_PURGE. Цей не ніс даних (len 0). sock_rfree() — деструктор прийнятих skb: він повертає пам’ять в облік сокета. Тож причина «drop» у трасуванні не завжди означає втрачений пакет; тут це звичайне закриття.

8. Follow it on your own machine8. Як простежити це на своїй машині

pwru answers one question: which functions did this packet pass through. It does not show everything:pwru відповідає на одне питання: через які функції пройшов цей пакет. Але не все:

  • Small functions the compiler inlined into their callers (ip_rcv_finish(), dst_input(), neigh_output()) run but never appear as separate calls.Дрібні функції, які компілятор вбудував у тих, хто їх викликає (ip_rcv_finish(), dst_input(), neigh_output()), виконуються, але окремими викликами не видно.
  • Functions that take no sk_buff, such as tcp_sendmsg(), are visible only in a call stack (--output-stack).Функції без аргументу sk_buff, як-от tcp_sendmsg(), видно лише в стеку викликів (--output-stack).
  • It shows the path, not the state around it: how full the queues are, what the counters say, which route and neighbour entry were used. For that there are ordinary tools, listed below.Він показує шлях, а не стан навколо: наскільки заповнені черги, що кажуть лічильники, який маршрут і запис сусіда використано. Only three kinds of calls, and they line up with the trace. connect() returns at once with EINPROGRESS: curl uses a non-blocking socket, so the SYN leaves (section 2) and the SYN-ACK and ACK (sections 3–4) are handled by the kernel while curl does something else. sendto() hands over the 71-byte request (section 5). Перший recvfrom() бачить порожню чергу прийому (EAGAIN); другий забирає 386 байтів — розмір даних відповіді, які tcp_queue_rcv() поклав у чергу в розділі 5.
